# 编排层

编排层决定一条买家消息能不能进模型、进哪一类 specialist、这一轮允许调哪些工具，并把引用、审批单、工单号推回前端。

代码在 `com.quanxiaoha.ai.robot.agent`。入口方法是 `AgentChatService.streamChat`。

总览：[架构说明.md](../../架构说明.md)。

## 一条消息在这一层的顺序

1. 用 `chatId` 作为会话号。没有就生成一个。
2. `LanguageDetector` 判 `zh`、`en` 或 `mixed`，`LanguageEvidenceService` 写入 `t_lang_event`。
3. `SafetyGateService.check`。拦住就记一条 `BLOCKED` 轨迹，把用户消息和拦截文案写入 `t_cs_message`，SSE 回 `type=blocked`，到此结束。
4. `AgentOrchestratorService.plan` 按关键词得到 specialist 和工具名列表。
5. `AgentTraceService.startRun` 写 `t_agent_run`。`ConversationStateService.ensureAiWorking` 把会话标成 `AI_WORKING`。
6. `filterCallbacks` 从全部工具里只留下白名单里的那些。
7. `ContextBoundToolCallback` 包住这些工具。工具真正执行时才把 `chatId` 绑到那条线程。
8. 系统提示里写上 specialist、风险、语种，以及 Widget 传来的 `customerContact`。提示要求查单和写操作使用这个联系方式，不要编造。
9. 模型流式输出正文。工具若产生引用、审批或工单，先放进按 `chatId` 存放的 `AgentSideChannel`。
10. 正文结束后 `drain(chatId)`，把这些事件作为 `type=meta` 的 SSE 发给前端，并写入消息表和轨迹。

## 安全门

类：`SafetyGateService`。上限 4000 字。

| 情况 | reason | 结果 |
|------|--------|------|
| 空白 | `EMPTY` | 不调模型 |
| 超长 | `TOO_LONG` | 不调模型 |
| 命中注入话术，例如 ignore previous、忽略之前、system prompt | `PROMPT_INJECTION` | 不调模型 |
| 普通退货、物流问题 | — | 放行 |

## 分流

类：`AgentOrchestratorService`。只看关键词，不再调一个模型来分类。先匹配到的分支生效。

| 关键词 | specialistKey | 本轮工具 | 写订单 |
|--------|---------------|----------|--------|
| 退货、退款、换货、取消订单、改地址、修改地址、收货地址、改址 | `return` | `queryOrder`、`createReturnRequest`、`requestRefundOrReplacement`、`requestAddressChange`、`escalateToHuman`、`refundPolicyRAG`、`translateSnippet` | 只建待审批 |
| 物流、快递、运单、到哪了、发货 | `order` | `queryOrder`、`trackLogistics`；话里有投诉、人工时再加 `escalateToHuman` | 否 |
| 订单、查单、`ord-` | `order` | `queryOrder`；投诉时再加 `escalateToHuman` | 否 |
| 商品、库存、多少钱、推荐、卫衣、袜子、保温杯、sku | `product` | `searchProductCatalog` | 否 |
| 政策、规则、保修、运费、怎么退、能否退、可以退吗 | `policy_rag` | `refundPolicyRAG`、`translateSnippet` | 否 |
| 投诉、转人工、找人工、真人，且上面都没中 | `handoff` | `escalateToHuman` | 否 |
| 其余 | `triage` | 查单、物流、商品、政策、翻译、转人工 | 否。默认没有写工具 |

「改一下 ORD-10003 的收货地址」含「收货地址」，进退货分支，不会先被 `ord-` 分到只能查单的订单分支。

后台页 `/admin/agent-workflow` 读的就是 `catalog()`，和上表是同一份说明。

## 工具在哪条线程执行

模型回调工具的线程，和组装 Flux 的线程不是同一条。

`ContextBoundToolCallback.call` 在调用前执行：

- `ToolAuditService.setConversationId(chatId)`，转人工才能把工单写到这个会话
- `ToolAuditService.setRunId(runId)`，工具步骤能挂到这次 Run
- `AgentSideChannel.bind(chatId)`，引用和审批单按会话号存放

调用结束后解开线程上的绑定。收尾用 `AgentSideChannel.drain(chatId)` 取事件，所以换线程也不会丢。

## 会话状态谁来改

| 状态 | 何时 |
|------|------|
| `AI_WORKING` | 本轮开始，或只是检索引用 |
| `NEEDS_APPROVAL` | 出现审批单事件 |
| `HUMAN_ASSIGNED` | 出现工单事件 |
| `RESOLVED` | 人工层结单，不在这一层写 |

## 这一层不做什么

- 不自己改订单金额和物流状态。
- 不把写工具的结果直接当成已退款。
- 不在白名单外调用工具。过滤发生在挂上模型之前。
